# Вводная информация по проекту «Aitest»

## Назначение проекта

Проект в рамках учебного курса: разработка конфигурации 1С с нуля. Приложение должно
уметь работать с **Kimi API** и на примере этой интеграции продемонстрировать различные
возможности современных LLM (текст, структурированные ответы, инструменты/функции и т. д. —
конкретный набор определяется заданиями курса).

## Цели

1. Создать работающее 1С-приложение, интегрированное с Kimi API.
2. Продемонстрировать на его примере возможности современных LLM.
3. Вести разработку по стандартам 1С (1С:Совместимо — стандарты разработки,
   требования к безопасности, асинхронность вызовов и т. п.).

## Порядок работы

- Каждый день открывается новое задание; задания идут по нарастающей сложности.
- Каждое следующее задание основывается на результатах предыдущих циклов.
- Разработка ведется итерационно, без «большого проектирования вперед»: объем работы
  на итерацию определяется текущим заданием.

## Роли и зоны ответственности

| Роль | Кто | Ответственность |
|---|---|---|
| Заказчик / приемщик | Пользователь | Постановка задач, корректировка предлагаемых решений, итоговая приемка результата. |
| Разработчик | Kimi Code (ИИ-агент) | Доработка конфигурации по стандартам 1С, ведение документации в `docs`, коммиты в ветку `dev`. |

## Рабочий процесс (definition of done на сессию)

1. Считать документацию из `docs` (погружение в контекст).
2. Получить задание, при необходимости уточнить/предложить решение.
3. Реализовать доработку в EDT-формате в `src/`.
4. Обновить документацию (`docs/`): новые знания, ограничения, решения, запись в дневник сессии.
5. Закоммитить изменения в ветку `dev`.
6. Передать результат на приемку заказчику.

## Git-процесс

- Локальный репозиторий git, ветки `dev` (разработка) и `main` (приемленный результат).
- Все изменения коммитятся в `dev` по итогам работы.
- Влитие в `main` выполняется только после приемки заказчиком и только по его явному запросу.

## Согласованные договоренности

1. **Проверка результата**: запуск клиента 1С и оценка результата работы — за заказчиком.
   Разработчик проверяет XML-корректность изменений и соответствие стандартам 1С.
   Ошибки, найденные при приемке, исправляются разработчиком.
2. **Хранение ключа Kimi API**: ключ хранится в константе конфигурации (значение вводится
   в базе, в репозиторий не коммитится).

## Архитектура и принятые решения

### День 1. Простой запрос к Kimi API

Состав реализации:

- Константа `KimiApiKey` («Ключ API Kimi», Строка(250), режим пароля) — хранение ключа;
- Общий модуль `KimiAPIСервер` (сервер, вызов сервера) — процедура `ОтправитьПростойЗапрос()`:
  формирует JSON по протоколу OpenAI-совместимого чата (`POST /v1/chat/completions`),
  выполняет HTTP-запрос средствами платформы, разбирает ответ;
- Общий модуль `KimiAPIКлиент` (клиент управляемого приложения) — асинхронный ввод вопроса
  (`ПоказатьВводСтроки`, модальность запрещена) и вывод ответа через `Сообщить()`;
- Общая команда `KimiПростойЗапрос` («Спросить у Kimi», панель навигации) — точка входа.

Принятые решения:

- Запрос к API выполняется только на сервере (объект `HTTPСоединение` на тонком клиенте
  недоступен); синхронность серверного HTTP-вызова допустима — запрет конфигурации касается
  синхронных вызовов расширений платформы и внешних компонент.
- Сервер API: `api.moonshot.ai` (глобальный endpoint Moonshot AI). Альтернатива: `api.moonshot.cn`.
- Модель: `kimi-k3.1-pro-highspeed` (семейство K3.1; модели `moonshot-v1-*` устарели).
  Имя модели и адрес сервера вынесены в отдельные функции (`ИмяМодели()`, `АдресСервера()`),
  точка смены — модуль `KimiAPIСервер`. Актуальный список моделей:
  https://platform.kimi.ai/docs/models.
- Ключ читается из константы на сервере; значение не выводится в интерфейс
  (константа в режиме пароля).

### Чат с историей диалога (основа интерфейса)

Выполнен до открытия нумерованных заданий курса (в дневнике ранее фигурировал как
«День 2»); по уточнению заказчика в нумерацию заданий курса не входит и служит
основой для их выполнения.

Заменяет простую команду Дня 1 (удалена по решению заказчика).

Состав реализации:

- Обработка `KimiЧат` («Чат с Kimi») с основной формой `ФормаЧата`:
  - реквизиты формы: `История` (таблица значений `Роль` + `Текст`) и `ТекущийВопрос`
    (многострочное поле ввода);
  - таблица истории с условным оформлением: сообщения «Вы» — синим, «Kimi» — зелёным
    (`ConditionalAppearance.dcssca`);
  - команды формы: «Отправить» (Ctrl+Enter), «Очистить историю»;
- Общий модуль `KimiAPIСервер`: функция `ОтправитьДиалог(Сообщения)` — принимает массив
  структур `{Роль, Текст}`, сериализует в `messages` API и отправляет; общая часть
  HTTP-запроса и разбора ответа вынесена из Дня 1;
- Общая команда `KimiЧат` («Чат с Kimi», панель навигации) — открывает форму обработки.

Принцип работы контекста: при каждом обращении вся история диалога из формы передаётся
на сервер и целиком уходит в `messages` запроса — модель видит полный диалог. История
хранится только в открытой форме (решение Дня 2); персистентное хранение (регистр
сведений) — кандидат на следующие итерации.

### День 2. Формат ответа

Задание курса: отправлять один и тот же запрос с разным уровнем контроля формата
ответа (без ограничений / с ограничениями / строгая схема), прогнать каждый вариант
несколько раз, сравнить ответы и проверить, парсятся ли они кодом.

Состав реализации:

- Форма `ФормаЧата`, группа «Параметры запроса»:
  - «Формат ответа» — `text` (без ограничений) / `json_object` (JSON Mode) /
    `json_schema` (Structured Output) → параметр `response_format`;
  - «Max tokens» — ограничение длины ответа (`max_tokens`; 0 — не задавать);
  - «Стоп» — стоп-последовательность (`stop`; в поле поддерживаются escapes `\n`, `\t`);
  - флажок «Добавить в запрос явное описание формата ответа» + многострочное поле —
    текст отправляется сообщением с ролью `system` (явное описание формата);
  - «Схема ответа (JSON Schema)» — видна только при формате «Строгая схема»;
- Кнопка «Проверить JSON» — последний ответ Kimi разбирается на сервере
  (`ЧтениеJSON`/`ПрочитатьJSON`), результат показывается неблокирующим предупреждением;
- Статусная строка под кнопками — токены запроса/ответа и `finish_reason`
  (при `length` выводится «обрезан по max_tokens»);
- Общий модуль `KimiAPIСервер`: `ОтправитьДиалог(Сообщения, Параметры)` принимает
  параметры формы и возвращает структуру (`Текст`, `ПричинаЗавершения`,
  `ТокеныЗапроса`, `ТокеныОтвета`, `ТокеныВсего`); для `json_schema` собирается
  `response_format` с `strict: true`.

Принятые решения:

- Уровни контроля комбинируются: явное описание формата (system) можно слать с любым
  `response_format`; `json_object` без описания в промпте допустим, но модель
  импровизирует поля — это тоже демонстрируется.
- Схема по умолчания — простой объект (`ответ`, `уверенность`, `ключевые_слова`):
  семейство k3.1 надёжно держит Structured Output, сложные конструкции (`anyOf`,
  `$ref`) намеренно не используем.
- «Проверка кодом» выполняется средствами платформы (`ПрочитатьJSON`), без БСП.
- Сравнение вариантов (несколько прогонов каждого) выполняет заказчик в клиенте;
  форма даёт для этого все ручки, включая счётчики токенов.

### День 3. Разные способы рассуждения

Задание курса: решить 5–10 задач с известными ответами четырьмя способами
промптинга при двух настройках рассуждения и сравнить, сколько задач решено
верно и сколько ушло токенов и времени; выявить, какие приёмы перестают давать
эффект, когда рассуждение включено.

Состав реализации:

- Справочник `KimiЗадачиРассуждений` («Задачи рассуждений»): наименование,
  текст задачи, эталонный ответ, категория (логическая/алгоритмическая/
  аналитическая); учебный набор из 8 классических задач наполняется кодом
  при первом открытии формы и кнопкой «Восстановить задачи»
  (предопределённые элементы не используем);
- Перечисления `KimiСпособыРассуждения` (`ПрямойОтвет`, `Пошагово`,
  `Самопромпт`, `Эксперты`) и `KimiУсилиеРассуждения` (`low` = минимальное,
  `max` = максимальное);
- Регистр сведений `РезультатыРассужденийKimi` (независимый, непериодический):
  измерения Задача/Способ/Усилие/Попытка; ресурсы — ответ модели, рассуждение
  (`reasoning_content`), составленный промпт, отметка «Верно», эталонная
  подсказка, токены (запрос/ответ/всего/рассуждение), время вызовов, сообщение
  об ошибке; реквизит «Дата запуска» связывает записи одного прогона;
- Отчёт `KimiРезультатыРассуждений` (СКД, автоформа): вариант «Сводка:
  способ × усилие» (группировка по способу и усилию: верных, всего попыток,
  суммы и средние по токенам и времени) и вариант «Детали по задачам»
  (задача × способ × усилие × попытка с текстами);
- Обработка `KimiРассуждение` («Способы рассуждения Kimi», общая команда
  в панели навигации), форма эксперимента: таблицы задач/способов/усилий
  с флажками (подмножества прогона), клиентский цикл по сценариям
  «задача × способ × усилие» через однократный обработчик ожидания (0,1 с):
  прогресс в статусе, кнопка «Остановить» работает между шагами; мониторинг
  результатов текущего прогона; колонка «Верно» редактируется и сразу пишется
  в регистр; при выборе строки показываются ответ, рассуждение и составленный
  промпт; кнопка «Сводка (отчёт)» открывает отчёт СКД;
- Общий модуль `KimiРассуждениеСервер`: `РешитьЗадачу(Задача, Способ, Усилие,
  ДатаЗапуска)` — собирает сообщения по способу, выполняет вызов(ы), вычисляет
  номер попытки (макс + 1 для ячейки), пишет регистр и возвращает структуру;
  тексты инструкций способов — функции модуля (точка настройки приёмов);
- Общий модуль `KimiAPIСервер` отрефакторен: общая сердцевина вынесена
  в экспортную `ВыполнитьЗапрос` (чатовая `ОтправитьДиалог` — обёртка);
  в параметры добавлено `УсилиеРассуждения` → верхнеуровневый `reasoning_effort`;
  в результат добавлены `Рассуждение`, `ТокеныРассуждения`, `ВремяМиллисекунд`.

Принятые решения:

- Первые объектные типы конфигурации: хранение персистентное (справочник +
  регистр), в отличие от истории чата (День 2). Повторные прогоны добавляют
  записи с номером попытки — сводка усредняет по попыткам (решение заказчика).
- «Верно» — ручная отметка заказчика: авто-подсказка «эталон найден в ответе»
  (регистронезависимый поиск эталона в тексте) лишь предзаполняет отметку
  при записи; итоговая таблица считается по «Верно».
- Рассуждение у K3.1 всегда включено (значения `low`/`high`/`max`, по
  умолчанию `max`) — Дни 1–2 фактически работали с `max`, не передавая поле;
  в Дне 3 усилие передаётся явно, «отключено» не имитируем.
- Способ «Самопромпт» — два последовательных вызова API; токены и время
  ячейки суммируются по обоим вызовам (честное сравнение стоимости приёма).
- Итоговая таблица дня — вариант настроек отчёта СКД, а не таблица на форме
  (решение заказчика); форма показывает только мониторинг текущего прогона.
- Выполнение прогона — клиентский цикл (без фоновых заданий): UI обновляет
  прогресс между шагами, текущий HTTP-вызов занимает форму на свою длительность.
